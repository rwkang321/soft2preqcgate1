# ResponseEntity<T> 와 빌더(Builder) 패턴 설명 보고서

- 대상 파일 1: `org.springframework.http.ResponseEntity` (Spring Framework 7.0 소스)
- 대상 파일 2: `com.preqcgate2.common.error.ApiExceptionHandler`
- 작업 종류: **설명 전용 (소스 코드 수정 없음)**. 아래에 나오는 코드는 모두 이해를 돕기 위한 참고 예시이다.

---

## 1. 전체 내용 설명

### 1-1. ResponseEntity 는 "HTTP 응답 한 건"을 담는 상자이다

HTTP 응답은 항상 세 부분으로 구성된다.

| HTTP 응답 구성 요소 | 예시 | ResponseEntity 에서 담당하는 곳 |
|---|---|---|
| 상태 코드 (Status Code) | `400 Bad Request` | `ResponseEntity` 의 `status` 필드 |
| 헤더 (Headers) | `Content-Type: application/json` | 부모 클래스 `HttpEntity` 의 `headers` |
| 본문 (Body) | `{"code":"E400", ...}` | 부모 클래스 `HttpEntity` 의 `body` (타입 = `T`) |

```java
public class ResponseEntity<T> extends HttpEntity<T> {   // HttpEntity = 헤더 + 본문
    private final HttpStatusCode status;                 // 여기에 상태 코드만 추가
```

즉 `ResponseEntity` = `HttpEntity`(헤더 + 본문) + 상태 코드 이다.

### 1-2. 파일의 구성 (위에서 아래 순서)

| 구역 | 내용 | 역할 |
|---|---|---|
| 생성자들 | `new ResponseEntity<>(body, headers, status)` 등 | 객체를 직접 만드는 전통적인 방법. 모든 생성자는 결국 맨 마지막 생성자 `(body, headers, statusCode)` 하나로 모인다. `MultiValueMap` 을 받는 생성자는 7.0 부터 사용 중단(Deprecated) 예정 |
| `getStatusCode()` | 상태 코드 반환 | 조회용 |
| `equals / hashCode / toString` | 비교, 출력 | `toString()` 결과 예: `<400 BAD_REQUEST Bad Request,ApiError[...],[]>` |
| 정적(static) 빌더 메서드들 | `status()`, `ok()`, `created()`, `badRequest()`, `notFound()` ... | **빌더 객체를 꺼내 주는 입구**. 실제 사용은 거의 이쪽으로 한다 |
| `HeadersBuilder` 인터페이스 | `header()`, `location()`, `eTag()`, `build()` ... | 헤더만 설정할 수 있는 빌더 규격 (본문 설정 불가) |
| `BodyBuilder` 인터페이스 | `contentType()`, `contentLength()`, `body()` | `HeadersBuilder` 를 상속 + 본문 설정 가능 |
| `DefaultBuilder` 클래스 (private) | 위 두 인터페이스의 실제 구현 | 상태 코드와 `HttpHeaders` 를 모아 두었다가 `body()` 호출 시 `new ResponseEntity<>(...)` 를 만든다 |

### 1-3. ApiExceptionHandler 에서 실제로 일어나는 일

```java
// ApiExceptionHandler.java 42행
return ResponseEntity.status(status)
        .body(new ApiError(code, status.value(), request.getRequestURI(), message, Instant.now()));
```

예: 입력 값 검증 실패(`MethodArgumentNotValidException`) 발생 시 실행 순서

1. `ResponseEntity.status(HttpStatus.BAD_REQUEST)`
   → 내부에서 `new DefaultBuilder(400)` 생성, `BodyBuilder` 타입으로 반환 (아직 응답 객체는 없음, "작업 중인 주문서" 상태)
2. `.body(new ApiError("E400", 400, "/api/users", "입력 값이 올바르지 않습니다!!!", 현재시각))`
   → `DefaultBuilder.body()` 가 `new ResponseEntity<>(apiError, headers, 400)` 를 만들어 반환
3. `@RestControllerAdvice` 이므로 Spring 이 `ApiError` 를 Jackson 으로 JSON 변환하여 전송

클라이언트가 받는 실제 응답:

```http
HTTP/1.1 400 Bad Request
Content-Type: application/json

{"code":"E400","status":400,"path":"/api/users","message":"입력 값이 올바르지 않습니다!!!","timestamp":"2026-10-03T00:03:00Z"}
```

(JSON 필드 이름은 `ApiError` 레코드의 구성 요소 이름을 따른다. 위 이름은 생성자 인자 순서에서 추정한 것이다.)

같은 결과를 생성자로 쓰면 다음과 같다. 두 방식의 결과는 완전히 같다.

```java
return new ResponseEntity<>(new ApiError(...), HttpStatus.BAD_REQUEST);
```

## 2. `ResponseEntity<T>` 의 `<T>` (제네릭, Generic)

### 2-1. 한 줄 정의

`<T>` 는 **"본문(body)에 들어갈 객체의 타입을, 클래스를 사용하는 쪽에서 정해서 끼워 넣는 빈칸"** 이다.
`T` 는 Type 의 첫 글자일 뿐이며, 이름 자체에 특별한 의미는 없다.

`ResponseEntity` 를 만든 Spring 개발자는 우리가 본문에 `ApiError` 를 넣을지 `UserDto` 를 넣을지 모른다. 그래서 타입 자리를 비워 두고, 사용하는 쪽에서 채우게 한 것이다.

### 2-2. 빈칸 `T` 를 채우는 실제 예

| 선언 | `T` 의 값 | `getBody()` 반환 타입 | 사용 장면 |
|---|---|---|---|
| `ResponseEntity<ApiError>` | `ApiError` | `ApiError` | 현재 `ApiExceptionHandler` |
| `ResponseEntity<String>` | `String` | `String` | 단순 문자열 응답 |
| `ResponseEntity<UserDto>` | `UserDto` | `UserDto` | 사용자 1명 조회 |
| `ResponseEntity<List<UserDto>>` | `List<UserDto>` | `List<UserDto>` | 사용자 목록 조회 |
| `ResponseEntity<Void>` | `Void` | 항상 `null` | 삭제 성공(204) 처럼 본문이 없는 응답 |
| `ResponseEntity<?>` | 알 수 없음 | `Object` 처럼 취급 | 상황에 따라 본문 타입이 다를 때 (권장하지 않음) |

```java
// 참고 예시 (Controller)
@GetMapping("/users/{id}")
public ResponseEntity<UserDto> getUser(@PathVariable Long id) {
    UserDto user = userService.findById(id);
    return ResponseEntity.ok(user);                 // T = UserDto
}

@GetMapping("/users")
public ResponseEntity<List<UserDto>> getUsers() {
    return ResponseEntity.ok(userService.findAll()); // T = List<UserDto>
}

@DeleteMapping("/users/{id}")
public ResponseEntity<Void> deleteUser(@PathVariable Long id) {
    userService.delete(id);
    return ResponseEntity.noContent().build();       // T = Void, 본문 없음
}
```

### 2-3. `<T>` 가 없다면 생기는 문제 (왜 쓰는가)

제네릭이 없던 시절처럼 본문 타입이 `Object` 라고 가정해 보자.

```java
// 가정: 제네릭이 없는 ResponseEntity
ResponseEntity response = handler.handleValidation(...);
Object body = response.getBody();
ApiError error = (ApiError) body;         // 매번 형 변환(cast) 필요
UserDto wrong = (UserDto) body;           // 컴파일은 통과 → 실행 중 ClassCastException 발생
```

제네릭을 쓰면:

```java
ResponseEntity<ApiError> response = handler.handleValidation(...);
ApiError error = response.getBody();      // 형 변환 불필요
UserDto wrong = response.getBody();       // 컴파일 오류 → 실행 전에 실수를 잡아 줌
```

정리: **`<T>` 의 목적은 "잘못된 타입 사용을 실행 전(컴파일 시점)에 잡는 것"과 "형 변환 코드 제거"** 이다.

### 2-4. 이 파일에 나오는 두 종류의 `<T>` 구분

```java
public class ResponseEntity<T> ...                      // (가) 클래스 제네릭
public static <T> ResponseEntity<T> ok(@Nullable T body) // (나) 메서드 제네릭
<T> ResponseEntity<T> body(@Nullable T body);            // (나) 메서드 제네릭
```

- (가) 클래스 제네릭: 객체를 선언할 때 `ResponseEntity<ApiError>` 처럼 정한다.
- (나) 메서드 제네릭: 반환 타입 앞의 `<T>` 는 "이 메서드 안에서만 쓰는 새 빈칸"이라는 선언이다. **메서드를 호출할 때 넘긴 인자의 타입으로 자동 결정**된다.

`ApiExceptionHandler` 42행에 적용하면:

```java
ResponseEntity.status(status)            // BodyBuilder : 이 시점에는 T 가 아직 없다
    .body(new ApiError(...));            // 인자가 ApiError → 이 호출의 T = ApiError
                                         // 반환 타입 = ResponseEntity<ApiError>  → 메서드 반환 타입과 일치
```

빌더(`BodyBuilder`)가 클래스 제네릭을 갖지 않고 `body()` 메서드에만 `<T>` 를 둔 이유: 상태 코드와 헤더를 설정하는 동안에는 본문 타입을 몰라도 되고, 마지막에 본문을 넣는 순간 타입을 정하면 되기 때문이다.

### 2-5. 클라이언트 쪽에서의 `<T>` (RestTemplate)

```java
ResponseEntity<UserDto> entity = restTemplate.getForEntity("https://example.com/users/1", UserDto.class);
UserDto user = entity.getBody();   // 응답 JSON 이 UserDto 로 변환되어 들어 있음
```

`UserDto.class` 를 넘기면 `T = UserDto` 로 결정되어, 받은 JSON 을 `UserDto` 로 변환해 준다.

## 3. 빌더(Builder) 패턴

### 3-1. 개념

**빌더 = "완성품을 바로 만들지 않고, 주문서에 항목을 하나씩 적은 뒤 마지막에 한 번에 완성품을 만들어 주는 도우미 객체"** 이다.

햄버거 주문에 비유하면:

```
주문서 받기      → ResponseEntity.status(400)        (빌더 생성)
패티 추가        → .header("X-Trace-Id", "abc")      (항목 설정, 주문서 그대로 반환)
치즈 추가        → .contentType(JSON)                (항목 설정, 주문서 그대로 반환)
주문 완료        → .body(apiError) 또는 .build()     (완성품 생성)
```

모든 빌더의 공통 특징 세 가지:

1. **설정 메서드는 `return this;`** → 자기 자신을 돌려주므로 점(`.`)으로 계속 이어 쓸 수 있다 (메서드 체이닝, Method Chaining).
2. **마지막 완성 메서드** (`build()`, `body()`, `toString()` 등) 가 진짜 결과물을 만든다.
3. **설정 순서, 생략 여부가 자유롭다** → 생성자처럼 인자 순서를 외울 필요가 없다.

`ResponseEntity` 의 `DefaultBuilder` 에서 1번 특징을 확인할 수 있다.

```java
@Override
public BodyBuilder header(String headerName, String... headerValues) {
    for (String headerValue : headerValues) {
        this.headers.add(headerName, headerValue);   // 주문서에 적기
    }
    return this;                                      // 주문서를 다시 돌려줌 → 체이닝 가능
}

@Override
public <T> ResponseEntity<T> body(@Nullable T body) {
    return new ResponseEntity<>(body, this.headers, this.statusCode);  // 완성품 생성
}
```

### 3-2. 빌더가 필요한 이유 (생성자의 한계)

```java
// 생성자 방식: 인자가 많아지면 순서를 헷갈리기 쉽다
new ApiError("E400", 400, "/api/users", "입력 값 오류", Instant.now());
//            ↑ code? path? 어느 것이 어느 것인지 이름이 보이지 않음
//            "E400" 과 "/api/users" 위치가 바뀌어도 둘 다 String 이라 컴파일 오류가 안 남

// 빌더 방식: 항목 이름이 코드에 그대로 보인다
ApiError.builder()
        .code("E400")
        .status(400)
        .path("/api/users")
        .message("입력 값 오류")
        .timestamp(Instant.now())
        .build();
```

---

### 3-3. 실제 사례 5가지

#### 사례 1. `StringBuilder` — 문자열을 조금씩 이어 붙이는 빌더 (이 파일의 `toString()` 안에 있음)

```java
// ResponseEntity.toString() 의 실제 코드
StringBuilder builder = new StringBuilder("<");
builder.append(this.status);          // "<400 BAD_REQUEST"
builder.append(' ');
builder.append(httpStatus.getReasonPhrase()); // "<400 BAD_REQUEST Bad Request"
builder.append(',');
...
return builder.toString();            // 완성 메서드 → 최종 String 생성
```

- 왜 빌더인가: `String` 은 한 번 만들면 바뀌지 않는(불변) 객체라서 `s = s + "a"` 를 반복하면 매번 새 문자열이 만들어진다. `StringBuilder` 는 내부 버퍼에 계속 적어 두다가 `toString()` 에서 한 번만 `String` 을 만든다.
- 체이닝도 가능: `new StringBuilder().append("<").append(400).append('>').toString();`
- 빌더의 핵심 = **"모아 두었다가 마지막에 한 번에 완성"**.

#### 사례 2. `ResponseEntity` 빌더 — 단계에 따라 쓸 수 있는 메서드가 제한되는 빌더 (현재 프로젝트 사용 중)

```java
// 400 + 본문
ResponseEntity.status(HttpStatus.BAD_REQUEST).body(apiError);

// 201 Created + Location 헤더 + 사용자 정의 헤더 + 본문
ResponseEntity.created(URI.create("/api/users/10"))
        .header("X-Trace-Id", "abc-123")
        .contentType(MediaType.APPLICATION_JSON)
        .body(newUser);

// 204 No Content : 본문 없음
ResponseEntity.noContent().build();
```

이 빌더의 특별한 점: **반환 타입으로 "본문을 넣을 수 있는지"를 강제한다.**

| 정적 메서드 | 반환 타입 | `.body(...)` 사용 가능? | 이유 |
|---|---|---|---|
| `status()`, `ok()`, `created()`, `badRequest()`, `internalServerError()` | `BodyBuilder` | 가능 | 본문이 있는 응답 |
| `noContent()` (204), `notFound()` (404) | `HeadersBuilder<?>` | **불가 (컴파일 오류)** | 204 는 HTTP 규약상 본문이 없어야 하고, 404 도 기본적으로 본문 없이 사용하도록 설계 |

```java
ResponseEntity.noContent().body(x);  // 컴파일 오류: HeadersBuilder 에는 body() 가 없음
ResponseEntity.notFound().build();   // 정상
```

참고로 404 에 본문(`ApiError`)을 넣고 싶으면 `ResponseEntity.status(HttpStatus.NOT_FOUND).body(apiError)` 처럼 `status()` 를 써야 한다. 현재 `ApiExceptionHandler.body()` 메서드가 바로 이 방식이다.

`HeadersBuilder<B extends HeadersBuilder<B>>` 라는 복잡한 선언의 의미:
`header()` 가 `HeadersBuilder` 가 아니라 **실제 하위 타입 `B` (= `BodyBuilder`)** 를 반환하게 하려는 장치이다.
이 장치가 없으면 `ResponseEntity.ok().header("A","1")` 의 결과가 `HeadersBuilder` 로 바뀌어서, 그 뒤에 `.body(...)` 를 이어 쓸 수 없게 된다.

```java
ResponseEntity.ok()              // BodyBuilder
        .header("A", "1")        // B = BodyBuilder 를 반환 → 여전히 BodyBuilder
        .body(data);             // 따라서 body() 호출 가능
```

#### 사례 3. Lombok `@Builder` — 내 DTO 에 빌더를 자동으로 붙이기

프로젝트 DTO 나 엔티티에 가장 많이 쓰는 방식이다.

```java
// 참고 예시: Lombok 사용 시
@Builder
public record ApiError(String code, int status, String path, String message, Instant timestamp) {}

// 사용
ApiError error = ApiError.builder()
        .code("E400")
        .status(400)
        .path(request.getRequestURI())
        .message("입력 값이 올바르지 않습니다!!!")
        .timestamp(Instant.now())
        .build();
```

`@Builder` 한 줄이 컴파일 시점에 아래와 비슷한 코드를 자동 생성한다 (직접 작성하면 이렇게 된다).

```java
public static ApiErrorBuilder builder() { return new ApiErrorBuilder(); }

public static class ApiErrorBuilder {
    private String code;
    private int status;
    private String path;
    private String message;
    private Instant timestamp;

    public ApiErrorBuilder code(String code)       { this.code = code; return this; }
    public ApiErrorBuilder status(int status)      { this.status = status; return this; }
    public ApiErrorBuilder path(String path)       { this.path = path; return this; }
    public ApiErrorBuilder message(String message) { this.message = message; return this; }
    public ApiErrorBuilder timestamp(Instant t)    { this.timestamp = t; return this; }

    public ApiError build() {
        return new ApiError(code, status, path, message, timestamp);
    }
}
```

- `ResponseEntity.DefaultBuilder` 와 구조가 똑같다: **필드 보관 → `return this` → 마지막에 생성자 호출.**
- 장점: 필드가 5개, 10개로 늘어나도 이름으로 지정하므로 순서 실수가 없다. 지정하지 않은 필드는 기본값(`null`, `0`)이 된다.
- 주의: 필수 값 검증은 자동으로 해 주지 않는다. 필요하면 레코드의 압축 생성자(compact constructor)에서 검증한다.

#### 사례 4. Java 표준 `HttpRequest.newBuilder()` — 불변(Immutable) 객체를 만드는 빌더

외부 API 를 호출할 때 사용하는 Java 11 이상 표준 라이브러리이다.

```java
HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://api.example.com/costs"))
        .header("Content-Type", "application/json")
        .header("Authorization", "Bearer " + token)
        .timeout(Duration.ofSeconds(5))
        .POST(HttpRequest.BodyPublishers.ofString(json))
        .build();                      // 완성 → 이후 request 는 절대 바뀌지 않음

HttpResponse<String> response = HttpClient.newHttpClient()
        .send(request, HttpResponse.BodyHandlers.ofString());   // 여기서도 <T> = String
```

- `HttpRequest` 에는 `setUri()`, `setHeader()` 같은 수정 메서드가 없다. **값을 바꿀 수 있는 것은 빌더뿐이고, `build()` 이후의 결과물은 읽기 전용**이다.
- 장점: 여러 스레드가 같은 `request` 를 동시에 써도 값이 바뀔 걱정이 없다.
- 빌더의 또 다른 목적 = **"설정 중에는 자유롭게 바꾸고, 완성된 뒤에는 고정"**.

#### 사례 5. Spring `UriComponentsBuilder` — 다른 빌더와 함께 쓰는 빌더 (`ResponseEntity.created()` 와 짝)

등록 API 에서 "새로 만든 자원의 주소"를 `Location` 헤더로 돌려줄 때 사용한다.

```java
// 참고 예시 (Controller)
@PostMapping("/users")
public ResponseEntity<UserDto> createUser(@RequestBody UserCreateRequest req,
                                          UriComponentsBuilder uriBuilder) {   // Spring 이 현재 요청 기준으로 주입
    UserDto saved = userService.create(req);

    URI location = uriBuilder
            .path("/api/users/{id}")      // 경로 추가
            .queryParam("view", "detail") // 쿼리 문자열 추가
            .buildAndExpand(saved.id())   // {id} 자리에 값 채우고 완성
            .toUri();                     // → http://localhost:8080/api/users/10?view=detail

    return ResponseEntity.created(location)   // 빌더 2: 201 + Location 헤더
            .body(saved);
}
```

클라이언트가 받는 응답:

```http
HTTP/1.1 201 Created
Location: http://localhost:8080/api/users/10?view=detail
Content-Type: application/json

{"id":10,"name":"홍길동"}
```

- 문자열 더하기(`"/api/users/" + id + "?view=" + v`)로 주소를 만들면 `/` 중복, 특수 문자 인코딩 누락 등의 실수가 생긴다. 빌더가 이를 대신 처리한다.
- **빌더 하나의 결과물(URI)이 다른 빌더(`ResponseEntity`)의 재료로 들어가는 구조**이다.

---

### 3-4. 다섯 가지 사례 비교 정리

| 사례 | 빌더 시작 | 설정 메서드 예 | 완성 메서드 | 결과물 | 이 사례에서 배울 점 |
|---|---|---|---|---|---|
| 1. `StringBuilder` | `new StringBuilder()` | `append()` | `toString()` | `String` | 모았다가 한 번에 완성 (성능) |
| 2. `ResponseEntity` | `ResponseEntity.status()` 등 | `header()`, `contentType()` | `body()`, `build()` | `ResponseEntity<T>` | 반환 타입으로 사용 가능한 단계를 제한 |
| 3. Lombok `@Builder` | `ApiError.builder()` | `code()`, `message()` | `build()` | `ApiError` | 필드가 많은 객체를 이름으로 안전하게 생성 |
| 4. `HttpRequest` | `HttpRequest.newBuilder()` | `uri()`, `header()`, `timeout()` | `build()` | `HttpRequest` | 완성품은 불변(수정 불가) |
| 5. `UriComponentsBuilder` | 주입 또는 `fromPath()` | `path()`, `queryParam()` | `buildAndExpand().toUri()` | `URI` | 빌더 결과를 다른 빌더에 전달 |

### 3-5. 빌더 판별 요령

코드에서 아래 모양이 보이면 빌더이다.

```
시작점( )  .설정( )  .설정( )  .설정( )  .완성( )
   ↑          ↑ 각각 자기 자신(this)을 반환       ↑ build(), body(), toString() 등 최종 객체 반환
```

`ApiExceptionHandler` 42행 `ResponseEntity.status(status).body(...)` 는 이 중 **"시작점 → 완성"** 만 있고 중간 설정 단계가 생략된 가장 짧은 형태의 빌더 사용이다.
